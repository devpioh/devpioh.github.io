## 개요

UniTask는 Cysharp에서 개발한, Unity의 비동기 처리를 위한 라이브러리다. C#의 `async/await`를 이용해 프레임 대기, 로딩 완료 대기, 여러 작업의 조합 등을 작성할 수 있다.

`UniTask`와 `UniTask<T>`는 구조체이며, 내부 작업 객체를 풀링해 관리 힙 할당을 줄인다. 다만 모든 사용 방식이 무할당인 것은 아니다. 사용자 코드의 객체 생성, 캡처하는 람다, 일부 변환, 빌드의 코드 최적화 설정 등에 따라 할당이 발생할 수 있으므로 실제 사용 환경에서 측정해야 한다. [UniTask의 할당 관련 설명](https://github.com/Cysharp/UniTask#allocation-on-profiler)

Unity의 비동기 API를 await하거나 `Task`, 코루틴과 연결할 수 있는 헬퍼도 제공한다. 각 변환은 실행 시점과 지원 범위가 다르므로 기존 코드의 동작을 확인하며 적용한다.

이 글은 UniTask 공식 문서와 Unity 6.0의 API 문서를 기준으로 정리한다. 아래의 `destroyCancellationToken` 예제는 **Unity 2022.2 이상과 UniTask 설치**를 전제로 한다.

## 동기(synchronous) / 비동기(asynchronous)

비동기는 작업의 완료를 기다리는 방식에 관한 개념이며, 별도 스레드에서 병렬로 실행한다는 의미는 아니다.

### 동기(synchronous)

호출한 함수가 반환되어야 다음 구문으로 진행한다. Unity 메인 스레드에서 오래 걸리는 동기 작업을 수행하면 입력과 화면 갱신도 지연될 수 있다.

### 비동기(asynchronous)

작업이 완료되지 않았을 때 실행을 중단하고, 나중에 완료된 지점부터 이어갈 수 있다. `await` 중에는 해당 메서드의 다음 구문이 실행되지 않지만, 기다리는 동안 스레드를 점유할 필요는 없다.

C#의 `async` 메서드는 **완료되지 않은 작업을 await하여 중단될 때까지 동기적으로 실행**된다. 이미 완료된 작업을 await하면 중단 없이 계속 실행할 수 있다. 따라서 `async`를 붙였다는 이유만으로 호출 즉시 제어권을 반환하거나 무거운 계산을 다른 스레드에서 실행하지는 않는다. [C# async 설명](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/keywords/async)

`Task`도 비동기 작업을 표현하는 타입이지, 스레드 자체가 아니다. 비동기 입출력과 `Task.Run`을 사용하는 CPU 작업을 구분해야 한다. [비동기 프로그래밍 시나리오](https://learn.microsoft.com/en-us/dotnet/csharp/asynchronous-programming/async-scenarios)

## PlayerLoop

PlayerLoop는 Unity가 프레임을 처리하면서 실행하는 여러 단계의 흐름이다. 입력 처리, 물리 업데이트, `Update`, `LateUpdate` 등의 처리가 이 흐름에 포함된다.

`PlayerLoopSystem`은 하위 시스템을 포함하는 계층 구조다. `PlayerLoop.GetDefaultPlayerLoop()`는 기본 구조를, `PlayerLoop.GetCurrentPlayerLoop()`는 커스텀 시스템을 포함한 현재 구조를 확인할 때 사용한다. [GetCurrentPlayerLoop 공식 문서](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/LowLevel.PlayerLoop.GetCurrentPlayerLoop.html)

UniTask의 `Delay`, `NextFrame` 같은 API는 PlayerLoop에 등록된 실행 지점을 사용한다. 메인 스레드에서 해당 작업을 이어갈 수 있지만, **UniTask를 사용한다는 사실만으로 모든 코드의 메인 스레드 실행이 보장되지는 않는다.** `SwitchToThreadPool()` 등으로 다른 스레드로 이동했다면 Unity 객체에 접근하기 전에 `SwitchToMainThread()`로 돌아와야 한다.

### Yield와 NextFrame

`UniTask.Yield()`는 지정한 PlayerLoop 단계의 다음 실행을 기다린다. 호출 위치에 따라 같은 프레임에서 재개될 수도 있다. 반드시 다음 프레임까지 기다리려면 `UniTask.NextFrame()`을 사용한다.

```cs
// async UniTask 메서드 안에서 사용하는 예제.
await UniTask.NextFrame();
await UniTask.DelayFrame(3);
```

`PlayerLoopTiming.Update`도 코루틴의 `yield return null`과 실행 위치가 완전히 같지는 않다. 프레임 내부의 순서에 의존하는 코드를 옮길 때는 대기 시간뿐 아니라 재개 시점도 확인한다. [UniTask PlayerLoop 설명](https://github.com/Cysharp/UniTask#playerloop), [대기 API 구현](https://github.com/Cysharp/UniTask/blob/master/src/UniTask/Assets/Plugins/UniTask/Runtime/UniTask.Delay.cs)

## vs Coroutine

두 방식 모두 프레임이나 시간, 다른 작업의 완료를 기다리는 흐름을 표현할 수 있다. 메인 스레드에서 오래 걸리는 동기 계산을 수행하면 어느 방식이든 프레임이 지연된다.

| 특징 | Coroutine | UniTask |
|-----|-----------|---------|
| 문법 | `IEnumerator` + `yield return` | `async UniTask` + `await` |
| 결과 반환 | 필드나 콜백 등 별도 전달 방식이 필요 | `UniTask<T>`로 결과 반환 |
| 취소 | 실행 주체에서 `StopCoroutine` 등으로 중지 | 토큰을 전달하고 작업이 취소 요청을 확인하는 협력적 취소 |
| 예외 처리 | `StartCoroutine` 호출을 try/catch로 감싸도 이후 프레임의 예외까지 잡지는 못함 | await한 작업의 예외를 try/catch로 처리 |
| 수명 관리 | GameObject 비활성화·MonoBehaviour 파괴 시 중지 | 필요한 수명에 맞춰 취소 토큰 등을 명시적으로 연결 |
| 할당 | 반복자 상태 머신과 대기 객체 등의 할당 | 구조체와 풀링으로 할당을 줄이지만 사용 방식에 따라 달라짐 |

### 기존 코루틴과 연결할 때

`IEnumerator`를 직접 await하거나 일반 `ToUniTask()`로 변환하는 방식에는 제한이 있다. `WaitForEndOfFrame`, `WaitForFixedUpdate`, `Coroutine` 반환을 지원하지 않으며, 재개 시점도 `StartCoroutine()`과 다르다.

기존 코루틴의 대기 동작을 유지하려면 `IEnumerator.ToUniTask(MonoBehaviour coroutineRunner)` 오버로드를 사용할 수 있다. 이 방식은 전달한 MonoBehaviour에서 실제 코루틴을 실행하므로 실행 주체의 수명도 함께 고려해야 한다. 변환 헬퍼가 작업의 취소와 리소스 정리까지 자동 해결하는 것은 아니다. [변환 제한](https://github.com/Cysharp/UniTask#ienumeratortounitask-limitation), [코루틴 변환 구현](https://github.com/Cysharp/UniTask/blob/master/src/UniTask/Assets/Plugins/UniTask/Runtime/EnumeratorAsyncExtensions.cs)

## 취소와 예외 처리 예제

다음 예제는 1초 뒤 GameObject를 위로 이동한다. 대기 중 오브젝트가 파괴되면 작업을 취소한다. `UniTaskExample.cs`로 저장해 GameObject에 추가한다.

```cs
using System;
using System.Threading;
using Cysharp.Threading.Tasks;
using UnityEngine;

public class UniTaskExample : MonoBehaviour
{
    private void Start()
    {
        // Unity 2022.2 이상. 객체가 살아 있을 때 토큰을 얻어 전달한다.
        MoveAfterDelayAsync(destroyCancellationToken).Forget();
    }

    private async UniTask MoveAfterDelayAsync(CancellationToken token)
    {
        try
        {
            await UniTask.Delay(
                TimeSpan.FromSeconds(1),
                cancellationToken: token);

            transform.position += Vector3.up;
        }
        catch (OperationCanceledException) when (token.IsCancellationRequested)
        {
            // 오브젝트 파괴에 따른 정상적인 취소로 처리한다.
        }
    }
}
```

`destroyCancellationToken`은 객체의 파괴에 연결된 토큰이다. 비활성화까지 작업의 끝으로 취급하려면 `OnEnable`에서 `CancellationTokenSource`를 만들고, `OnDisable`에서 취소·해제하는 등 별도의 수명 관리가 필요하다. [destroyCancellationToken](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/MonoBehaviour-destroyCancellationToken.html)

토큰은 작업을 강제로 종료하는 장치가 아니다. 하위 비동기 호출에도 전달해야 하며, 직접 작성한 긴 루프에서는 적절한 위치에서 취소 요청을 확인해야 한다. `Delay` 같은 작업은 기본적으로 PlayerLoop에서 요청을 확인한다. API에 따라 `cancelImmediately` 옵션이 있지만 추가 처리 비용을 고려해 선택한다. [Delay API](https://cysharp.github.io/UniTask/api/Cysharp.Threading.Tasks.UniTask.html)

예제의 `.Forget()`은 완료를 기다리지 않는 실행을 명시하고 예외를 관찰하는 헬퍼다. 기본적으로 처리되지 않은 예외는 UniTask의 예외 처리 경로로 전달된다. 결과나 완료 순서가 필요한 호출에서는 `await`를 사용한다. [Forget API](https://cysharp.github.io/UniTask/api/Cysharp.Threading.Tasks.UniTaskExtensions.html)

## vs Unity Awaitable

Unity의 `Awaitable`은 **Unity 2023.1에서 도입**되었다. 이는 Unity 비동기 API를 위한 지원이며, C#의 `async/await` 자체를 Unity 6부터 사용할 수 있게 되었다는 의미는 아니다. [Unity의 Await 지원 설명](https://docs.unity3d.com/kr/2023.2/Manual/AwaitSupport.html)

두 타입 모두 await 및 제네릭 결과 반환을 지원하고, 풀링으로 할당 부담을 줄인다. Unity 6.0 API 기준의 주요 차이는 다음과 같다.

| 특징 | Awaitable | UniTask |
|-----|-----------|---------|
| 도입 방식 | Unity 내장 API | 별도 패키지 |
| 반환 타입 | `Awaitable`, `Awaitable<T>` | `UniTask`, `UniTask<T>` |
| 프레임 대기 | 다음 프레임, FixedUpdate, 프레임 끝 등의 API | 프레임 수 대기와 세부 PlayerLoopTiming 지정 등을 지원 |
| 여러 작업 조합 | Unity 6.0 Awaitable에는 `WhenAll`에 해당하는 내장 API가 없음 | `WhenAll`, `WhenAny` 등을 제공 |
| 취소 | 주요 대기 API의 `CancellationToken` 및 인스턴스의 `Cancel()` | 토큰을 받는 대기 API와 `WithCancellation` 등의 확장 메서드 |
| 스레드 전환 | `BackgroundThreadAsync`, `MainThreadAsync` | `SwitchToThreadPool`, `SwitchToMainThread` |
| 작업 추적 도구 | UniTaskTracker에 해당하는 전용 창은 제공하지 않음 | UniTaskTracker 제공 |

Awaitable의 `NextFrameAsync`, `WaitForSecondsAsync` 등도 취소 토큰을 지원한다. 두 라이브러리 모두 API별로 취소 지원 방식과 완료 시점이 다를 수 있으므로, 사용하는 메서드의 시그니처를 확인한다. [NextFrameAsync](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Awaitable.NextFrameAsync.html), [WaitForSecondsAsync](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Awaitable.WaitForSecondsAsync.html)

### 같은 작업을 여러 번 await할 때

일반적인 `UniTask`와 `Awaitable`은 같은 작업 인스턴스를 여러 번 await하지 않는 것을 기본 규칙으로 삼는다. 풀링된 내부 상태를 재사용할 수 있기 때문이다.

UniTask에서 완료 결과를 다시 기다려야 한다면 `.Preserve()`로 결과를 보존하는 방식 등을 사용할 수 있다. 여러 호출자가 동시에 기다리는 설계라면 `UniTaskCompletionSource` 등 해당 사용을 지원하는 수단을 선택한다. [UniTask의 재대기 규칙](https://github.com/Cysharp/UniTask#basics-of-unitask-and-asyncoperation)

```cs
// async UniTask 메서드 안에서 사용하는 예제.
var task = UniTask.DelayFrame(1).Preserve();
await task;
await task; // 보존된 완료 결과를 사용한다.
```

Awaitable도 단순히 확장 메서드로 감싼다고 같은 인스턴스를 재사용할 수 있는 것은 아니다. 결과를 여러 곳에 공유해야 한다면 원본을 한 번만 소비하고, `Task` 등 반복 대기를 지원하는 별도 표현으로 전달하는 설계가 필요하다. [Awaitable의 풀링 제약](https://docs.unity3d.com/kr/2023.2/Manual/AwaitSupport.html)

기본적인 대기 기능과 외부 의존성 최소화가 중요하다면 Awaitable을, 작업 조합과 다양한 PlayerLoop 제어가 필요하다면 UniTask를 검토할 수 있다. 지원 Unity 버전과 프로젝트에서 필요한 기능을 기준으로 선택한다.
