## 개요

AI 코딩 에이전트에 기능 구현을 맡기면 코드를 작성하는 것 외에도 여러 작업이 필요하다. 기존 구조를 읽고, 필요한 도구를 실행하고, 테스트 실패의 원인을 찾아 수정해야 한다. 작업이 길어지면 무엇을 완료했고 어떤 판단을 내렸는지도 유지해야 한다.

**하네스(Harness)**는 모델이 이런 작업을 이어갈 수 있도록 감싸는 실행 시스템이다. OpenAI는 Codex 하네스의 역할로 컨텍스트 수집, 도구 사용, 대화 상태 관리, 샌드박스와 승인 정책 적용 등을 설명한다. [Codex as a platform](https://developers.openai.com/blog/codex-as-a-platform)

이 글에서는 **에이전트가 목표를 달성하고 결과를 검증할 수 있도록 지침, 도구, 실행 환경, 피드백 과정을 설계하고 개선하는 작업**을 하네스 엔지니어링으로 정리한다. OpenAI의 Codex 공식 문서와 개발자 블로그를 바탕으로, 개발 프로젝트에 적용할 수 있는 형태로 설명한다.

> 문서 확인 기준일은 2026-09-23이다. 아래의 분류와 예제는 이해를 돕기 위해 구성한 것이며, Codex가 요구하는 고정된 프로젝트 구조는 아니다.

## 프롬프트, 컨텍스트, 하네스의 차이

세 개념은 서로 연결되어 있지만 설계할 때 주목하는 대상이 다르다. 다음처럼 구분하면 이해하기 쉽다.

| 구분 | 주로 다루는 질문 | 예시 |
| ---- | ---- | ---- |
| 프롬프트 엔지니어링 | 어떤 작업을 어떤 조건으로 요청할 것인가? | 입력 조건, 변경 범위, 완료 기준을 명확하게 작성 |
| 컨텍스트 엔지니어링 | 판단에 필요한 정보를 언제 제공할 것인가? | 관련 코드, 설계 문서, 오류 로그를 필요한 시점에 제공 |
| 하네스 엔지니어링 | 작업을 실행하고 확인하며 이어갈 구조를 어떻게 만들 것인가? | 도구 연결, 실행 권한, 테스트, 상태 기록, 실패 후 재시도 설계 |

예를 들어 “경로 탐색 버그를 수정해라”라는 요청에 재현 조건과 기대 결과를 추가하는 것은 프롬프트를 개선하는 일이다. 관련 코드와 이동 규칙을 제공하는 것은 컨텍스트를 구성하는 일이다.

여기에 테스트를 실행할 환경, 실패 로그를 읽는 도구, 수정 가능한 파일 범위, 결과를 판정하는 기준까지 연결하면 하네스 관점의 작업이 된다. 같은 모델을 사용하더라도 이런 조건에 따라 실제로 끝낼 수 있는 작업의 범위가 달라질 수 있다.

## Codex의 작업 루프

OpenAI의 장시간 작업 사례는 Codex의 흐름을 계획, 코드 수정, 도구 실행, 결과 관찰, 실패 수정, 문서와 상태 갱신의 반복으로 설명한다. 테스트 결과와 로그가 다음 판단의 입력으로 돌아오는 구조다. [Run long horizon tasks with Codex](https://developers.openai.com/blog/run-long-horizon-tasks-with-codex)

```text
목표와 완료 기준
    ↓
관련 코드와 문서 확인 → 계획 → 코드 수정
                              ↓
                     테스트·빌드·도구 실행
                              ↓
                          결과 확인
                              ├─ 실패 → 원인 분석 → 수정 후 재검증
                              └─ 통과 → 완료 기준 확인 → 결과 정리
```

여기서 모델은 다음 행동을 판단하고, 하네스는 도구 호출을 실행하거나 정책에 따라 제한하며 결과를 다시 모델에 전달한다. 개발자는 프로젝트에서 사용할 도구와 검증 기준을 준비한다.

**테스트를 실행할 수 있다는 사실만으로 요구사항 검증까지 보장되지는 않는다.** 예를 들어 빌드 성공은 코드가 컴파일된다는 근거지만, 경로 탐색 결과가 최단 경로라는 근거는 별도로 필요하다.

Codex를 사용할 때는 이 실행 시스템을 처음부터 직접 구현할 필요가 없다. 이미 제공되는 작업 루프 위에 프로젝트의 지침과 도구, 검증 절차를 연결하는 것부터 시작할 수 있다.

## 1. AGENTS.md로 프로젝트의 기준 전달하기

`AGENTS.md`는 Codex가 작업할 때 참고하는 지속적인 지침이다. 매번 대화에 반복해서 적는 프로젝트의 규칙이나 검증 명령을 파일로 남길 수 있다.

Codex는 실행 시작 시 전역 지침과 프로젝트 지침을 모은다. 프로젝트에서는 루트부터 현재 작업 디렉터리까지 확인하고, 각 디렉터리에서 `AGENTS.override.md`, `AGENTS.md`, 설정된 대체 파일 이름 순으로 찾는다. 디렉터리마다 최대 하나를 사용하며, 더 가까운 디렉터리의 지침이 앞선 지침을 덮어쓸 수 있다. [AGENTS.md 공식 문서](https://learn.chatgpt.com/docs/agent-configuration/agents-md)

따라서 저장소 전체에 적용할 내용은 루트에 두고, 특정 영역에만 필요한 내용은 해당 영역의 지침으로 분리할 수 있다. 별도로 만든 문서는 필요한 상황과 경로를 지침에 적어 찾아갈 수 있게 한다.

예를 들어 C# 경로 탐색 라이브러리의 루트 `AGENTS.md`는 다음과 같이 작성할 수 있다.

```markdown
# 프로젝트 작업 지침

## 구조

- src/Pathfinding: 경로 탐색 라이브러리
- tests/Pathfinding.Tests: 단위 테스트
- 이동 규칙이나 탐색 방식을 변경할 때는 docs/pathfinding.md를 참고한다.

## 변경 기준

- 공개 API의 이름과 반환 형식을 유지한다.
- 경로를 찾지 못하면 빈 목록을 반환한다.
- 버그 수정에는 수정 전 실패하고 수정 후 통과하는 회귀 테스트를 추가한다.

## 검증

- 빌드: dotnet build Pathfinding.sln
- 테스트: dotnet test tests/Pathfinding.Tests/Pathfinding.Tests.csproj
- 테스트는 로컬 데이터만 사용하며 외부 서비스에 접근하지 않는다.
- 실행하지 못한 검증은 이유와 함께 결과에 기록한다.
```

좋은 지침은 프로젝트의 특수한 조건을 짧고 구체적으로 전달한다. 설계 문서 전체를 복사하거나 모든 작업에서 모든 문서를 읽도록 요구하면, 작은 수정에도 불필요한 정보가 늘어난다. 문서의 역할과 읽어야 할 상황을 연결하는 편이 낫다. [지침과 프롬프트를 재검토하는 OpenAI 가이드](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra)

## 2. Skills로 반복 작업의 절차 묶기

`AGENTS.md`에 프로젝트의 공통 기준을 둔다면, **스킬(Skill)**에는 특정 작업에 필요한 절차와 자료를 묶을 수 있다. 예를 들어 성능 측정, 데이터 마이그레이션 검토, 릴리스 노트 작성처럼 반복해서 사용하는 작업이 해당한다.

스킬은 `SKILL.md`를 중심으로 구성하며, 필요한 경우 스크립트와 참고 문서를 함께 둔다. Codex는 먼저 이름과 설명을 확인하고, 해당 스킬을 사용하기로 결정하면 본문을 읽는다. 이를 **점진적 공개(Progressive Disclosure)**라고 한다. [Skills 공식 문서](https://learn.chatgpt.com/docs/build-skills)

저장소에서 공유하는 스킬의 구성 예시는 다음과 같다.

```text
.agents/
└── skills/
    └── pathfinding-benchmark/
        ├── SKILL.md
        ├── scripts/
        │   └── run-benchmark.ps1
        └── references/
            └── benchmark-cases.md
```

`SKILL.md`에는 이름과 사용 조건을 포함한다.

```markdown
---
name: pathfinding-benchmark
description: 경로 탐색 구현 변경 전후의 실행 시간과 할당량을 비교할 때 사용한다.
---

# 경로 탐색 성능 비교

1. references/benchmark-cases.md에서 측정 조건을 확인한다.
2. 동일한 지도, 난수 시드, 빌드 설정으로 변경 전후를 측정한다.
3. scripts/run-benchmark.ps1로 결과를 수집한다.
4. 경로의 정확성과 성능 측정값을 함께 보고한다.
```

위 스크립트와 측정 문서는 프로젝트에서 별도로 구현해야 한다. 스킬 파일이 절차를 설명하더라도 실행 도구와 입력 데이터가 준비되어 있어야 작업할 수 있다.

또한 사용 조건을 “경로 탐색과 관련된 모든 작업”처럼 넓게 잡으면 단순한 설명 요청에도 성능 측정을 시작할 수 있다. **언제 필요한 절차인지**를 명확하게 쓰는 것이 중요하다.

## 3. 도구와 실행 환경 준비하기

에이전트가 코드를 이해하더라도 필요한 런타임이나 의존성이 없으면 실행 결과를 확인할 수 없다. 프로젝트를 내려받은 뒤 빌드와 테스트를 재현할 수 있는 환경을 준비해야 한다.

| 준비할 항목 | 확인할 내용 |
| ---- | ---- |
| 런타임과 의존성 | 필요한 SDK 버전과 패키지 복원 방법이 명확한가? |
| 실행 명령 | 빌드와 테스트를 사람이 추가 조작하지 않아도 실행할 수 있는가? |
| 입력 데이터 | 버그 재현에 필요한 샘플과 테스트 데이터가 있는가? |
| 관찰 수단 | 오류 로그, 테스트 결과, 필요한 화면을 확인할 수 있는가? |
| 외부 자료 | 필요한 문서와 서비스에 접근할 수 있는가? |

Codex에는 파일을 읽고 수정하거나 명령을 실행하는 기능이 있으며, 외부 도구와 컨텍스트는 **MCP(Model Context Protocol)**를 통해 연결할 수도 있다. 공식 문서는 문서 조회나 브라우저·개발 도구와의 연결을 예로 든다. [MCP 공식 문서](https://learn.chatgpt.com/docs/extend/mcp)

예를 들어 테스트 실패 시 종료 코드와 오류 메시지가 남으면 에이전트는 실패 위치를 확인할 수 있다. 화면 동작을 검증해야 한다면 브라우저 조작과 스크린샷 같은 관찰 수단도 필요하다. 도구를 연결하는 목적은 **다음 판단에 필요한 증거를 얻는 것**이다.

MCP는 외부 도구를 연결하는 방법이며, 하네스 전체를 의미하지는 않는다. 로컬 파일과 테스트 명령만으로 충분한 프로젝트라면 그것부터 준비해도 된다.

## 4. 샌드박스와 승인 정책으로 작업 범위 정하기

Codex는 샌드박스와 승인 정책을 구분한다. 두 설정은 에이전트가 어디까지 자율적으로 실행할 수 있는지를 함께 결정한다. [승인과 보안 공식 문서](https://learn.chatgpt.com/docs/agent-approvals-security)

| 구분 | 역할 |
| ---- | ---- |
| 샌드박스(Sandbox) | 실행 명령이 접근할 수 있는 파일, 쓰기 범위, 네트워크 등의 기술적 경계를 제한 |
| 승인 정책(Approval Policy) | 권한 확대 등이 필요할 때 승인을 요청하는 방식을 결정 |

로컬 Codex의 사용자 설정 파일인 `~/.codex/config.toml`에 작성하는 예시는 다음과 같다.

```toml
sandbox_mode = "workspace-write"
approval_policy = "on-request"

[sandbox_workspace_write]
network_access = false
```

이 설정은 작업 공간 안의 파일 수정과 명령 실행을 허용하고, 샌드박스 내 명령의 네트워크 접근을 제한한다. 경계를 벗어나는 작업이 필요하면 승인 절차를 거칠 수 있다. 실제 허용 범위는 실행 환경과 조직의 관리 정책도 함께 확인해야 한다. [샌드박스 공식 문서](https://learn.chatgpt.com/docs/sandboxing)

`AGENTS.md`에 “이 디렉터리만 수정한다”라고 적는 것은 행동 지침이다. 파일 접근을 기술적으로 제한하려면 샌드박스와 도구 권한을 설정해야 한다. 외부 서비스에 연결한 MCP 도구의 권한 역시 해당 서비스와 도구 설정에서 확인한다.

프로젝트에서는 로컬 테스트처럼 반복 실행할 작업과 배포·외부 데이터 변경처럼 별도 판단이 필요한 작업의 경계를 정해 두면 좋다. 그러면 허용된 범위의 작업을 계속 진행하면서 필요한 시점에 결과를 검토할 수 있다.

## 5. 긴 작업의 상태를 파일에 남기기

여러 단계에 걸친 작업에서는 대화 기록 외에도 요구사항, 결정 이유, 남은 작업을 확인할 수 있어야 한다. OpenAI의 장시간 작업 사례는 명세, 계획, 실행 지침, 진행 상태를 Markdown 파일로 나누어 유지했다. [장시간 작업의 프로젝트 메모리 사례](https://developers.openai.com/blog/run-long-horizon-tasks-with-codex)

이를 작은 프로젝트에 적용한다면 다음 정도로 시작할 수 있다.

| 파일 | 기록할 내용 |
| ---- | ---- |
| `docs/task.md` | 목표, 변경 범위, 완료 조건 |
| `docs/plan.md` | 단계별 작업과 검증 방법 |
| `docs/status.md` | 완료 항목, 결정 이유, 실패 원인, 다음 작업 |

이 파일 이름들은 예시이며, 파일을 생성하는 것만으로 Codex가 모두 자동으로 읽는 것은 아니다. 작업 요청이나 `AGENTS.md`에서 관련 경로와 사용 시점을 알려 준다.

상태 기록에는 “테스트 완료”보다 “어떤 명령으로 무엇을 확인했는지”를 남긴다. 예를 들어 실패한 입력과 수정 이유를 함께 기록하면, 작업을 다시 시작할 때 같은 조사를 반복할 가능성을 줄일 수 있다.

작은 수정이라면 별도 계획 문서까지 만들 필요는 없다. 작업의 길이와 복잡도에 맞춰 필요한 기록만 유지한다.

## 적용 예시: 경로 탐색 버그 수정

앞에서 작성한 `AGENTS.md`와 빌드·테스트 환경이 준비된 C# 프로젝트를 가정하자. 다음은 작업 요청의 예시다.

```text
장애물이 있는 격자에서 경로가 없는데도 경로가 반환되는 문제를 수정한다.

관련 자료:
- 구현: src/Pathfinding
- 테스트: tests/Pathfinding.Tests
- 이동 규칙: docs/pathfinding.md

변경 범위:
- 상하좌우 이동과 한 칸당 비용 1을 유지한다.
- 공개 API와 반환 형식을 변경하지 않는다.

완료 조건:
- 목표가 벽으로 둘러싸인 지도에서는 빈 목록을 반환한다.
- 시작점과 목표점이 같은 이동 가능한 칸이면 좌표 하나를 반환한다.
- 경로가 존재하면 양 끝점을 포함하고 벽을 통과하지 않는다.
- 경로의 최소 비용은 작은 격자의 BFS 기준 결과와 비교한다.
- 버그를 재현하는 회귀 테스트와 기존 테스트가 통과한다.

완료 후 변경 이유, 실행한 검증, 확인하지 못한 내용을 정리한다.
```

이 요청이 실제 작업으로 이어지려면 다음 조건이 함께 갖춰져야 한다.

1. **정보**: 에이전트가 구현 코드와 이동 규칙을 읽을 수 있다.
2. **도구**: 필요한 .NET SDK와 패키지가 준비되어 테스트를 실행할 수 있다.
3. **피드백**: 실패한 테스트의 입력, 기대값, 실제값을 확인할 수 있다.
4. **검증 기준**: 빈 경로, 경계 조건, 최단 비용을 확인하는 테스트가 있다.
5. **검토 자료**: 변경된 코드와 실행 결과를 사람이 확인할 수 있다.

에이전트가 반복해서 같은 조건을 놓친다면 해당 조건을 회귀 테스트로 남긴다. 특정 모듈의 의존 방향을 자주 어긴다면 설계 문서와 함께 정적 검사나 아키텍처 테스트로 확인할 수도 있다. **반복되는 실패를 다음 실행에서 감지할 수 있는 장치로 바꾸는 것**이 하네스를 개선하는 방법이다.

## 하네스도 평가하고 유지보수하기

코드의 단위 테스트는 구현의 동작을 확인한다. 여기에 에이전트가 적절한 스킬을 선택했는지, 필요한 검증을 실행했는지, 불필요한 파일을 만들지 않았는지를 확인하면 작업 흐름 자체를 평가할 수 있다.

OpenAI의 스킬 평가 가이드는 **요청 → 실행 기록과 산출물 → 검사 → 비교 가능한 점수**의 흐름을 제안한다. 결과뿐 아니라 과정, 스타일, 효율도 관찰 대상으로 둔다. [Testing Agent Skills Systematically with Evals](https://developers.openai.com/blog/eval-skills)

프로젝트에서는 대표 작업과 과거의 실패 사례를 모아 다음 항목을 비교할 수 있다.

| 평가 대상 | 확인할 예시 |
| ---- | ---- |
| 결과 | 요구사항과 테스트를 만족했는가? |
| 과정 | 필요한 도구와 검증을 사용했는가? |
| 변경 범위 | 관련 없는 코드나 설정을 수정하지 않았는가? |
| 효율 | 불필요한 재시도, 실행 시간, 토큰 사용이 늘지 않았는가? |

모델이나 지침을 바꿀 때 같은 초기 코드와 작업 조건에서 비교하면 개선 여부를 판단하기 쉽다. 한 번의 성공만으로 결론을 내리기보다, 중요한 사례는 반복해서 실행하여 결과의 편차도 살펴본다.

지침을 계속 추가하는 것만이 개선은 아니다. 사용하지 않는 스킬, 중복 규칙, 오래된 실행 명령을 정리하고 실제 실패와 관련된 내용만 남긴다. OpenAI도 모델이 발전함에 따라 과도한 지침과 문서 읽기 요구를 재검토하도록 권한다. [지침 유지보수 가이드](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra)

하네스 엔지니어링에서는 사람이 목표와 제약, 검증 기준을 설계하고 에이전트의 실행 결과를 바탕으로 환경을 개선한다. 처음에는 **짧은 프로젝트 지침, 재현 가능한 실행 환경, 명확한 완료 조건**부터 준비하고, 반복 작업과 실패가 쌓이는 부분을 보완하면 된다.
